Manuel de Dépannage, Diagnostics & FAQ

Méthodologies de diagnostic pas à pas, résolution des codes d'erreur courants, commandes d'inspection des bus matériels et réponses aux questions fréquentes.

1. Dépannage Modbus TCP & RTU

Lorsqu'un équipement ne répond pas, le Journal système affiche en direct un message d'erreur explicite. Consultez le tableau ci-dessous pour identifier et corriger la cause :

Journal de diagnostic en direct : Tentatives de lecture Modbus, avertissements CRC et exportation immédiate des journaux.
Message d'erreur Cause probable Action corrective
connection refused (ECONNREFUSED) L'adresse IP est joignable, mais le service Modbus TCP est désactivé ou écoute sur un autre port. Activez Modbus TCP dans les réglages de l'onduleur ou de la borne (par ex. Huawei FusionSolar → Paramètres Dongle → Modbus TCP : Sans restriction). Vérifiez le port (502 ou 1502).
i/o timeout L'adresse IP cible est hors ligne, filtrée par un pare-feu/VLAN ou l'équipement est en veille profonde. Testez l'accessibilité par ping <ip>. Certains onduleurs PV purs coupent leur carte réseau la nuit lorsque la production solaire tombe à 0 W.
modbus: response slave id mismatch L'équipement utilise un identifiant d'unité esclave Modbus différent. Valeurs par défaut : Solis = 1 ; Huawei = 1 ou 2 ; SMA = 3 ou 126 ; SolarEdge = 1 ; GoodWe = 247. Consultez la notice de l'appareil.
modbus: exception 'Illegal Data Address' Le modèle interroge un registre non pris en charge par le micrologiciel actuel de l'onduleur. Mettez à jour le firmware de l'onduleur via l'application constructeur ou vérifiez le modèle d'appareil sélectionné.
CRC check failed / framing error Parasites électromagnétiques sur le bus RS485, débit en bauds incorrect ou absence de terminaison. Vérifiez la vitesse RS485 (9600 vs 19200 vs 115200), installez des résistances de terminaison de 120Ω aux deux extrémités du bus et utilisez une paire torsadée blindée.

2. Diagnostic du Compteur Communicant P1 DSMR

Débit en bauds & Inversion du signal série

Les compteurs DSMR 5.0 récents (Fluvius, ORES, RESA, Sibelga et compteurs néerlandais) fonctionnent à 115200 bauds, 8 bits de données, sans parité, 1 bit d'arrêt (8N1) et émettent un signal logique inversé. Les anciens compteurs DSMR 2.2 / 3.0 émettent à 9600 bauds, 7 bits, parité paire, 1 bit d'arrêt (7E1). Assurez-vous que votre câble USB-P1 intègre bien un circuit actif d'inversion de signal.

Tester le flux brut P1 dans le Terminal

Ouvrez le terminal Cockpit sur le port 9090 et exécutez les commandes suivantes :

Bash / Terminal 
# 1. Vérifier que le convertisseur série USB est bien détecté
ls -l /dev/ttyUSB*

# 2. Configurer la vitesse du port série (DSMR 5.0)
stty -F /dev/ttyUSB0 115200 cs8 -cstopb -parenb

# 3. Lire le télégramme brut (doit afficher du texte lisible commençant par '/')
cat /dev/ttyUSB0

# Exemple de sortie attendue :
# /FLU5\253769484_A
# 1-0:1.8.1(001234.567*kWh)
# 1-0:1.7.0(01.250*kW)
# 1-0:31.7.0(005*A)
# !52C1

3. Diagnostics de Connexion Borne VE OCPP

Symptôme Cause racine Action corrective
L'état de la borne reste « Hors ligne » La borne ne parvient pas à joindre l'URL WebSocket ou ne résout pas mDNS. Configurez l'adresse IP directe dans la borne : ws://192.168.1.50:8887/<ChargerID> (ou :8080/api/ocpp/<ChargerID>) plutôt que ems.local.
Erreur WebSocket 404 / 400 Bad Request Le ChargePoint ID présent dans l'URL ne correspond pas au champ configuré dans GEMS. Vérifiez que l'identifiant final de l'URL correspond exactement au ChargePoint ID saisi lors de l'ajout de l'appareil dans GEMS.
Le courant de charge ne varie pas La borne ignore les profils SetChargingProfile. Assurez-vous que la borne est réglée en mode « Auto » ou « CSMS externe / Smart Charging » dans l'application constructeur et qu'aucun forçage manuel local n'est actif.
Diagnostic par Scanner : Vérification des adresses IP locales, noms d'hôtes et ports ouverts (502 Modbus, 80/443 HTTP, 8887/8080 OCPP).

4. Diagnostics SSD NVMe & Bootloader (Raspberry Pi 5)

Si votre Raspberry Pi 5 ne détecte pas le SSD M.2 NVMe ou échoue à démarrer sur la carte d'extension PCIe, suivez cette grille de vérification :

Symptôme Cause racine Diagnostic & Résolution
Écran noir au démarrage / LED ACT immobile L'EEPROM est restée sur la configuration d'usine BOOT_ORDER=0xf41 sans détection PCIe. Flashez l'utilitaire officiel Bootloader → NVMe/PCIe Boot sur une carte MicroSD avec Raspberry Pi Imager et démarrez 5 secondes jusqu'à l'écran HDMI vert fixe.
lspci n'affiche aucun périphérique NVMe La nappe FPC est inversée, mal verrouillée ou dtparam=pciex1 est absent. Vérifiez que les contacts dorés sont orientés vers l'intérieur côté ports USB/Ethernet du Pi 5 et que /boot/firmware/config.txt contient dtparam=pciex1 et dtparam=pciex1_gen=2.
Message noyau : pcieport link down Défaut d'intégrité du signal ou chute de tension d'alimentation. Utilisez impérativement l'alimentation officielle 27W USB-C PD (5,1V / 5,0A). Les chargeurs 15W classiques provoquent une sous-tension lors de l'initialisation PCIe.
lsblk n'affiche pas /dev/nvme0n1 SSD mal inséré dans le connecteur M.2 ou disque M.2 SATA non compatible NVMe. Réinsérez fermement le SSD M.2 NVMe à 30° et serrez la vis M2. Exécutez sudo modprobe nvme et sudo dmesg | grep -i nvme dans Cockpit.
Commandes d'inspection NVMe (Terminal Cockpit) 
# 1. Vérifier si le contrôleur PCIe détecte le SSD NVMe :
lspci -v

# 2. Vérifier si le périphérique bloc NVMe est reconnu :
lsblk -f

# 3. Lire l'ordre d'amorçage EEPROM et l'état PCIe :
sudo rpi-eeprom-config

# 4. Inspecter les messages du noyau liés au bus PCIe/NVMe :
sudo dmesg | grep -i -E "pci|nvme"

5. Diagnostics d'Intégrité SQLite & Stockage

GEMS exploite le mode Write-Ahead Logging (WAL) de SQLite et des tampons en mémoire vive pour prévenir toute corruption disque. Vous pouvez contrôler l'état de la base depuis le terminal :

Commandes de diagnostic SQLite 
# Ouvrir la base de données SQLite
sqlite3 /opt/gems/gems.db

-- 1. Vérifier l'activation du mode WAL (doit renvoyer 'wal')
PRAGMA journal_mode;

-- 2. Contrôler l'intégrité interne (doit renvoyer 'ok')
PRAGMA integrity_check;

-- 3. Examiner l'état des points de contrôle WAL
PRAGMA wal_checkpoint(PASSIVE);

-- 4. Compter le nombre total d'enregistrements de mesures
SELECT COUNT(*) FROM measurements;

.exit

6. Diagnostic des Alertes & Webhooks

Pour vérifier que votre URL alert_webhook_url reçoit correctement les notifications :

Test Webhook via Curl 
# Envoyer une alerte de test via l'API locale GEMS :
curl -X POST http://localhost:8080/api/notifications/test \
  -H "Content-Type: application/json" \
  -d '{"message": "Notification de test envoyée par GEMS"}'

7. Diagnostics Cloud & GRID-EMS-SERVER

Pour le détail complet des schémas JSON, de la procédure d'appairage et de la topologie réseau, consultez le Guide de Connexion GRID-EMS-SERVER ou téléchargez le Manuel Serveur Imprimable (PDF).

Symptôme / Message d'erreur Cause sous-jacente Procédure de diagnostic & résolution
Handshake failed: dial tcp lookup... Échec de résolution DNS sur l'interface réseau du Raspberry Pi. Vérifiez la passerelle et les serveurs DNS dans le terminal Cockpit : curl -Iv https://ems.newenergygrid.com/api/status.
HTTP 401 Unauthorized Clé secrète révoquée ou unité supprimée depuis le portail central. Générez un nouveau jeton d'appairage dans le portail cloud et relancez l'appairage dans Paramètres → Serveur Cloud.
Telemetry push network error: timeout Port sortant 443 bloqué ou perte de paquets importante sur la liaison Internet. Vérifiez l'ouverture du port TCP 443 en sortie sur le pare-feu local ainsi que le câble Ethernet.
Commandes distantes non appliquées Commandes en file d'attente jusqu'au prochain cycle de synchronisation. Consultez le tableau d'audit des commandes cloud dans Paramètres → Serveur Cloud. L'exécution intervient lors du cycle télémétrique suivant (2s à 5s).
Journal du service Cloud 
# Suivre en direct l'activité du démon de synchronisation cloud
sudo journalctl -u gems -f | grep CloudManager

8. Foire Aux Questions (FAQ)

Pourquoi n'y a-t-il pas d'API constructeur automobile ni de lecture du SoC véhicule ?

Par philosophie d'ingénierie, GEMS s'appuie exclusivement sur des mesures matérielles locales en temps réel. Les API cloud des constructeurs automobiles sont instables, sujettes à des coupures fréquentes, à des quotas restrictifs et peuvent décharger la batterie 12V du véhicule. GEMS pilote la charge de façon fiable directement via la borne de recharge.

Pourquoi la charge CPU n'apparaît-elle pas dans Infos système ?

GEMS est strictement optimisé pour réduire au minimum la consommation mémoire et processeur sur Raspberry Pi. L'interrogation continue des compteurs système depuis l'interface web est volontairement omise. Les diagnostics matériels complets restent accessibles à tout moment dans Cockpit sur le port 9090.

Quel est le temps de réponse du mode zéro-export ?

Les compteurs d'énergie sont interrogés chaque seconde. Dès qu'une injection vers le réseau est détectée, les consignes d'écrêtement d'onduleur et de modulation des bornes VE sont transmises immédiatement afin de maintenir l'export aussi proche de 0 W que physiquement possible.

Comment réinitialiser le mot de passe administrateur Cockpit ?

Ouvrez une session terminal par SSH ou clavier branché en direct, puis exécutez sudo passwd admin (ou votre nom d'utilisateur Linux) et saisissez deux fois le nouveau mot de passe.

Comment récupérer après une mise à jour interrompue ?

Si une mise à jour logicielle a été coupée par une panne de courant, ouvrez le terminal Cockpit et exécutez sudo dpkg --configure -a suivi de sudo apt-get install -f.

Le système fonctionne-t-il sans connexion Internet ?

Oui ! Toutes les boucles de régulation (mode Éco, écrêtage capacitaire flamand, zéro-export, protection du disjoncteur, Modbus et OCPP natif) s'exécutent à 100 % localement sur le Raspberry Pi sans aucune dépendance cloud. En cas de coupure Internet, la dernière grille tarifaire EPEX sur 24 heures reste utilisée.
